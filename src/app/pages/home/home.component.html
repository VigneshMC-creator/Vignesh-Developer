ABOUT

How I approach development.

I like to understand the complete request path before changing a single method.

I believe good software should do more than pass a test or deliver a feature. It should be easy to understand, safe to run, efficient under load and straightforward to change as requirements evolve. Before writing code, I try to understand the problem, the existing architecture and the impact a change could have on other parts of the application.

I aim for simple, purposeful code: remove unnecessary duplication, reuse well-defined components and services, and avoid abstractions that make a solution harder to follow. Fewer lines are useful only when the result stays readable, testable and clear to the next developer.

Performance starts with choosing the right place to do the work. I look for repeated processing, avoid unnecessary database calls, pay attention to EF Core queries and SQL execution, and use asynchronous I/O for operations that wait on external resources. I prefer measuring a bottleneck before optimizing it.

Security belongs in the design, not as a final patch. That means validating untrusted input, enforcing authorization at the right boundaries, following least-privilege access, protecting configuration and secrets, and returning useful errors without exposing internal details.

For dependable APIs and server-side applications, I value clear contracts, backward compatibility, environment-based configuration, structured logging, predictable error handling, cancellation support and tests for important success and failure paths. The goal is software that is maintainable, deployable and reliable—not code that only works on one developer's machine.
